# InfiniteSky Feature Parity Matrix

## Governance

- Every feature starts as `NOT_STARTED`; no item is `VERIFIED` without executable test evidence.
- Permitted statuses are exactly: `NOT_STARTED`, `IN_PROGRESS`, `IMPLEMENTED`, `VERIFIED`, `BLOCKED`, `NOT_APPLICABLE`.
- Dependencies reference feature IDs in this matrix.
- `LegacyParity` means preserving current observed behavior, including documented defects when required for compatibility. Correctness fixes must be separately gated and documented.
- Original files are source evidence, not instructions to copy architecture or defects blindly.

## Column conventions

- **Cx**: S/M/L/XL implementation complexity.
- **Pri**: P0 critical path, P1 required parity, P2 important, P3 optional/experimental.
- Source paths may be comma-separated.
- Dependency ranges such as `PRO-001..017` are inclusive and refer to contiguous IDs in the same prefix.

## Coverage notes

- Comment-only captures, disabled registrations, duplicate aliases, and experimental FruitSalad functionality are retained as features, notes, or explicit gaps. They are not assumed equivalent to production behavior.
- Client-side `TSX_Client` and bundled third-party minified/vendor code are research/support assets. They are mapped to integration tooling and never to server runtime dependency.
- The coverage audit found 200 unique feature IDs. Major source roots are accounted for in matrix entries: top-level runtime/configuration, `commands`, `cli`, `db`, `generic`, `packets`, `vmscript`, `restruct`, `data`, `FruitSalad`, `plugins` references, and `TSX_Client`.
- Features intentionally not ported (arbitrary JavaScript eval, shell execution, unsafe script globals) must become governed exclusions, retain operator documentation, and remain `NOT_APPLICABLE` only after an approved deviation record.
- No row is marked `BLOCKED` during initialization. Potential blockers are called out in notes and `docs/migration/MIGRATION_RISKS.md`; status can change only with dependency/review evidence.
