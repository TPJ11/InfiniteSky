# Residual Security and Reliability Risks

These risks remain after the Prompt 24 baseline review. They are not hidden by the passing foundation test suite. See the detailed evidence and compatibility decisions in [SECURITY_FINDINGS.md](./SECURITY_FINDINGS.md).

| Risk | Component | Impact / preconditions | Existing mitigation | Remaining exposure / reason unresolved | Recommended next action | Release impact | Status |
|---|---|---|---|---|---|---|---|
| RSR-001 / SEC-002 | Legacy account credential storage | Database or backup read access exposes stored plaintext passwords. | Database disabled by default; .NET uses fixed-time comparison and clears mutable credential buffers. | The original schema/authenticator stores and compares plaintext. Changing only .NET would break legacy Node compatibility; no live account corpus or coordinated migration exists. | Restrict DB/backup access; approve and test a migration that updates every active authenticator and account-reset workflow. | Block public production use of credential-bearing data until access controls/migration are accepted. | OPEN |
| RSR-002 / SEC-001 | Game-client TCP transport | An observer on an untrusted path can capture credentials when a listener is enabled and reachable. | Networking disabled by default and loopback-bound by default. | The legacy client protocol has no TLS/encryption; no original client or compatible tunnel was tested. | Keep listener on a trusted network or use an approved VPN/tunnel; design a versioned encrypted transport only with client compatibility evidence. | Block exposure to untrusted networks. | OPEN |
| RSR-003 / SEC-003 | MongoDB transport | Remote credentials/data may be observed if a non-TLS remote URI is used on an observable path. | MongoDB disabled by default; empty default connection string; bounded connection/operation timeouts. | Validator does not require TLS; no deployment URI or MongoDB server was available. | Require TLS and validate certificates for remote MongoDB; verify least-privilege roles and the actual URI before enabling. | Block unprotected remote database connections. | CONDITIONAL |
| RSR-004 / SEC-004 | Login status responses | Reachable clients can distinguish unknown accounts from wrong passwords and enumerate account names. | Status values match source behavior; attempts still require a correct credential to authenticate. | Generic failure would change the legacy response mapping; no client evidence supports that change. | Retain only with explicit compatibility acceptance; pair with network isolation and an approved login-abuse policy. | Low residual; disclose in threat model and do not claim enumeration resistance. | OPEN - compatibility constrained |
| RSR-005 | Authentication abuse controls | Repeated guesses can be submitted by an actor who can reach the listener; no per-account/IP rate limiter was found. | Connection admission maximum, per-connection request serialization, authentication timeout, idle timeout. | These controls are not an attempt-rate limit. No representative workload or lockout policy exists; arbitrary thresholds can affect NAT-shared legitimate clients. No successful attack was demonstrated. | Define and test attempt-rate/lockout policy and abuse telemetry before public exposure. | Do not expose publicly without an explicit operator decision. | OPEN - potential risk, not a confirmed vulnerability |
| RSR-006 / REL-001 | Session ownership and account `active` marker | If multiple instances share a database, process-local session registries can admit the same account on different instances; one instance's startup reset can clear all active flags. | Atomic one-session-per-account enforcement inside one process; startup behavior is configurable. | Distributed session coordination is not implemented or tested. The documented model is single-process, and the legacy global reset is enabled by default. | Keep to one instance; if scaling is required, design/test cross-process ownership and stale-active recovery before deployment. | Block multi-instance deployment against shared account data. | CONDITIONAL |
| RSR-007 | Administration and scripting | Future handlers could expose privilege escalation, arbitrary code execution, or unbounded work if enabled without controls. | No .NET remote GM command dispatcher, script runtime, or plugin loader is implemented. | Their absence blocks features; it is not evidence that the legacy Node command/script environment is safe. Legacy scripts run with server-process privileges and are not sandboxed. | Keep those features unavailable; require session-bound authorization, trusted-source policy, and isolation review before implementing. | Exclude from release scope unless separately implemented and verified. | BLOCKED |
| RSR-008 | Character and gameplay ownership | Forged character IDs or state mutations could cross accounts if future packet handlers trust client claims. | Internal player activation checks ownership and session lifetime in component tests; no client gameplay workflow is wired. | No network character selection/world entry/gameplay test exists, so packet-level enforcement cannot be claimed. | Require ownership derived from the authenticated session for each future action; add cross-account regression tests before enabling handlers. | Block any claim of gameplay security or playable release. | BLOCKED |
| RSR-009 | Persistence compatibility and recovery | Legacy BSON, concurrent writes, interruption, or Mongo outage may cause data loss/inconsistency. | Typed filters/mappers, selected ownership checks, operation timeouts, and synthetic BSON tests. | Live Mongo tests were skipped; no production fixture, backup/restore rehearsal, or recovery guarantee was established. | Run opt-in tests against disposable MongoDB, verify representative sanitized legacy BSON, and rehearse isolated backup/restore. | Block persistence compatibility/recovery claims. | BLOCKED |
| RSR-010 | Production deployment | Misbound listeners, weak process identity, leaked configuration, untested service setup, or missing backups could expose data or prevent recovery. | Defaults are disabled/loopback; environment configuration and limitations are documented. | No production-style service/container, firewall, secret-store, filesystem-permission, or clean-machine deployment test was run. | Complete a deployment rehearsal with least-privilege identity, protected config, firewall, logging, backups, and shutdown procedure. | Not ready for final release preparation. | NOT TESTED |

## Compatibility-sensitive security limitations

The legacy login protocol transports credentials in raw TCP and the legacy account schema stores plaintext credentials. Adding TLS to the game listener or changing the password representation without client/server migration could break original-client or mixed-version behavior. Distinct login statuses also reveal account existence. These are explicit residuals, not claims that the risks were fixed.

No test established original-client compatibility, public-network safety, production MongoDB security, rate-limit behavior, multi-instance session correctness, administrative authorization, script sandboxing, or lossless player shutdown. See [production hardening checklist](./PRODUCTION_HARDENING_CHECKLIST.md) and [operational recovery](./OPERATIONAL_RECOVERY.md).
